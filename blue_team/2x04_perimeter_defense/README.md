# 2x04 Perimeter Defense

This MedDefense lab starts with a network baseline, turns a four-zone design into firewall rules, and uses offline traffic analysis to investigate suspicious activity. It also tests a local DNS filter that blocks listed domains while allowing normal resolution.

## Review answers

### Task 16 — Defense in Depth at the Network Layer

1. **Option 4.** Endpoint telemetry gives visibility into individual hosts. Network controls cover traffic between systems and can block unauthorised connections even if a host has already been compromised.
2. **Option 2.** Inline IPS can block malicious traffic in real time, but false positives on blocking rules can also interrupt legitimate services. IDS and offline replay let the team evaluate and tune detections without dropping production packets.
3. **Option 4.** Segmentation limits the blast radius of a compromised medical device by restricting which hosts and services it can reach, giving the team time to detect and respond.

### Task 17 — IDS versus IPS Trade-offs

Offline IDS replay is deterministic because the same PCAP, Suricata version, rules and settings produce repeatable detections, and it is low risk because it runs outside the live traffic path. An inline IPS can drop malicious packets in real time before they reach their destination. If we turn every alert into a drop rule, a false positive could block legitimate traffic and interrupt a hospital service like the EHR. Before going inline, I’d review the Task 9 alert report (`suricata_alerts.json`) for noisy signatures, check the Task 10 validation results (`rule_validation.json`) for expected rule hits, and use the Task 11 packet findings (`pcap_findings.json`) to confirm what traffic triggered the alerts. I’d start by replaying known-good and malicious captures in the lab, then monitor mirrored hospital traffic in IDS alert-only mode to measure false positives and tune the rules. Before enforcing any drops, I’d test inline forwarding with blocking disabled on a non-critical segment, verify service connectivity, latency and packet loss, and test the rollback before gradually enabling a few high-confidence drop rules.

### Task 18 — Segmentation in Healthcare Environments

Endpoint-only protection leaves these medical devices exposed because they can’t run security agents, and taking them offline for routine patching can disrupt patient care. Default-deny segmentation limits the blast radius by blocking every cross-zone connection except the ones the devices need for clinical work. I’d allow DICOM only to the PACS server and HTTPS only to the EHR, with a specific source, destination, protocol and port for each rule and a documented clinical reason for allowing it. The devices are still vulnerable, and a compromised device could attack peers on the same VLAN or misuse an allowed connection. I’d compare the intended flows in `segmentation_rules.json` with the rules in `nftables.conf` and the loaded rules verified in `nftables_apply_log.json`. To verify enforcement in practice, I’d review connection test results and firewall logs showing that DICOM and HTTPS work on the authorised paths and that other cross-zone attempts are dropped.

### Task 19 — PCAP Analysis Methodology

I’d start with conversation metadata, Suricata alert summaries, DNS queries, TLS SNI and file transfer indicators to scope the investigation before inspecting individual packets. First, I’d use `tshark` to rank TCP and UDP conversations by byte count, then replay the same PCAP offline with a fixed Suricata ruleset and use `jq` to filter `eve.json` for alerts matching those hosts and time windows. Next, I’d use `tshark` to extract DNS queries, then TLS SNI, then HTTP and SMB file transfer indicators for the shortlisted conversations. In `pcap_findings.json`, I’d use the bytes and timing in `top_conversations` to prioritise sessions, `long_dns_labels` to flag possible DNS tunnelling, and `file_transfers` to look for evidence of an outbound transfer. This metadata-first order saves time because it shows which hosts, protocols and time windows deserve attention, so I can use `tcpdump` to inspect just the relevant packets instead of reading the whole capture packet by packet. I’d use `alerts[].signature` and `alerts[].severity` in `suricata_alerts.json` to prioritise the session and escalate if the alert matches the same endpoints and time as packet evidence of suspicious outbound activity.
