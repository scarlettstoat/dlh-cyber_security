## 1. Purpose

This policy establishes requirements for the creation, use, management, protection, storage, and technical implementation of passwords and authentication controls at SecureBank Financial Services.

The objective is to reduce the risk of unauthorised access, credential theft, account compromise, and fraud while supporting compliance with PCI DSS, SOX, FFIEC guidance, and current security best practices.

## 2. Scope

### 2.1 Applicability

This policy applies to:

- [x] All employees
- [x] Contractors and consultants
- [x] Third-party vendors with authorised access
- [x] Privileged and administrative users
- [x] Developers and system administrators

### 2.2 Systems/Assets Covered

This policy applies to authentication used for:

- Core banking systems

- Cloud services

## 3. Policy Statements

### 3.1 Password Requirements

Passwords must be sufficiently long, difficult to guess, and screened against known weak or compromised values.

**Requirements:**

- Passwords used as a single authentication factor must contain at least **15 characters**.
- Systems must support passwords of at least **64 characters** where technically possible.
- Long passphrases are encouraged.
- Passwords must be checked against a blocklist of common, expected, and known compromised passwords.
- Passwords must not contain easily guessed information such as the user's name, username, account number, company name, or simple keyboard patterns.
- Passwords must not be reused across personal and company accounts.
- Users should use unique passwords for separate company systems.
- Passwords must not be silently truncated.
- For systems subject to PCI DSS, passwords must also meet applicable PCI DSS composition requirements.
- SecureBank will not require arbitrary complexity rules such as mandatory special characters unless required by a specific system, regulation, or approved security standard.

### 3.2 Password Management

Passwords must be managed through approved and secure processes.

**Requirements:**

- Users must never share passwords or authentication codes.
- Passwords must be changed immediately when compromise is suspected or confirmed.
- Passwords must be reset following a confirmed credential breach or when directed by Information Security.
- Routine password changes will not be required solely because a fixed period has passed unless required by regulation or a specific system requirement.
- Password reset procedures must verify the identity of the requester.
- Temporary passwords must be unique and expire after first use or within a short defined period.
- Password reset links or tokens must be single-use and time-limited.
- Security questions based on publicly discoverable information must not be used as the sole recovery method.
- Password changes, resets, lockouts, and authentication events must be logged.

#### Account Lockout

- Systems must limit repeated failed authentication attempts.
- PCI-scoped systems must lock or otherwise restrict a user ID after no more than **10 failed attempts**.
- Where lockout is used for PCI-scoped systems, the minimum lockout duration must be **30 minutes** or until the user's identity is verified by an authorised administrator.
- Other systems should use rate limiting, progressive delays, or risk-based controls to reduce brute-force and credential-stuffing attacks.

#### Session Timeouts

- Privileged and high-risk systems must automatically lock or terminate inactive sessions.
- Users must re-authenticate before sensitive actions such as changing authentication factors, modifying payment details, or carrying out privileged operations.
- Technical timeout values are defined in Section 12.

### 3.3 Multi-Factor Authentication (MFA)

MFA must be used to reduce reliance on passwords and strengthen access security.

**MFA is mandatory for:**

- All privileged and administrative accounts
- All remote access and VPN connections
- All access into the Cardholder Data Environment (CDE)
- Core banking systems
- Administrative systems
- Cloud administration consoles
- High-risk access to customer or financial information
- Other systems designated by Information Security

**Approved MFA methods include:**

- FIDO2/WebAuthn security keys or passkeys
- Approved hardware cryptographic tokens
- Approved authenticator applications using time-based one-time passwords (TOTP)
- Certificate or PKI-based authentication
- Approved biometric authentication when combined with another independent factor

Phishing-resistant MFA, such as FIDO2/WebAuthn or PKI-based authentication, should be preferred for privileged and high-risk accounts.

SMS and voice-based one-time codes must not be the preferred MFA method and may only be used where stronger methods are not technically feasible and the risk has been accepted.

Users must never approve an MFA request they did not initiate.

### 3.4 Password Storage and Protection

Passwords must be protected against disclosure in storage and transmission.

**Requirements:**

- Passwords must never be stored in plaintext.
- Passwords must not normally be stored using reversible encryption.
- Application passwords must be stored using an approved password hashing algorithm and a unique salt.
- The preferred hashing algorithm is **Argon2id**.
- Fast general-purpose hashes such as MD5, SHA-1, or unsalted SHA-256 must not be used for password storage.
- Passwords and authentication credentials must only be transmitted over approved encrypted channels.
- Passwords must not be written into source code, scripts, configuration files, tickets, email, or documentation.
- Application secrets must be stored in an approved secrets-management platform.

#### Password Managers

- Employees may use only company-approved password managers.
- Password managers must be protected with MFA.
- Users should use unique passwords for separate systems.
- Shared credentials must only be used where specifically approved and must be stored in an approved enterprise password or privileged access management solution.

### 3.5 Privileged Accounts

Privileged accounts require enhanced controls because compromise could cause significant harm to SecureBank systems or data.

**Requirements:**

- Privileged accounts must be separate from standard user accounts.
- Administrative accounts must not be used for routine email, web browsing, or normal office work.
- MFA is mandatory for all privileged access.
- Phishing-resistant MFA should be used where technically supported.
- Privileged credentials must be managed through an approved Privileged Access Management (PAM) solution.
- PAM should support controlled credential checkout, credential rotation, access logging, and session monitoring.
- Shared administrator accounts are prohibited unless there is a documented technical necessity and compensating controls are approved.
- Default vendor passwords must be changed before systems are placed into production.
- Privileged access must follow the principle of least privilege.
- Privileged access rights must be reviewed regularly and removed when no longer required.
- Emergency or break-glass accounts must be tightly controlled, monitored, and reviewed after use.

## 5. Compliance

### 5.1 Monitoring

Compliance will be monitored through:

- Authentication and access logs
- Failed-login and account-lockout events
- MFA enrolment and usage reports
- Password-policy configuration reviews
- Compromised-password screening
- PAM activity and privileged session logs
- Security incident monitoring
- Periodic account and access reviews

### 5.2 Reporting

Material authentication weaknesses, repeated violations, and credential-related incidents must be reported to the CISO and relevant management.

Issues involving PCI DSS, SOX, or other regulatory requirements must also be escalated to Compliance and Internal Audit where appropriate.

### 5.3 Auditing

Authentication controls must be audited at least annually and when significant changes are made to identity systems or critical applications.

Audits should verify:

- Password length and configuration settings
- MFA coverage
- Password storage methods
- Privileged account controls
- PAM operation
- Account lockout settings
- Access reviews
- Logging and monitoring
- Regulatory compliance

## 6. Enforcement

### 6.1 Violations

Violations of this policy may result in:

- Verbal warning
- Written warning
- Mandatory security awareness training
- Forced credential reset
- Suspension of access privileges
- Removal of privileged access
- Disciplinary action up to and including termination
- Legal or regulatory action where applicable

Serious violations involving intentional credential sharing, unauthorised privileged access, or deliberate bypass of security controls may result in immediate escalation.

### 6.2 Reporting Violations

Suspected violations or credential compromise must be reported immediately to:

**Information Security Operations / IT Service Desk**

Critical incidents affecting banking systems, privileged accounts, customer data, or the CDE must be escalated according to the Incident Response Policy.

---

## 7. Exceptions

### 7.1 Exception Process

Exceptions to this policy require:

1. A written request to the Information Security / IAM Team
2. Business and technical justification
3. A documented risk assessment
4. Compensating controls where applicable
5. Compliance review where regulated systems are affected
6. Formal approval by the Policy Owner or authorised risk owner
7. Documentation of the approved exception

No exception may override a mandatory legal or regulatory requirement without approval from the appropriate Compliance and Legal functions.

### 7.2 Exception Duration

All exceptions must have a defined end date.

Exceptions must be reviewed at least annually, and high-risk exceptions must be reviewed more frequently.

# 12. Technical Password Standards

This section defines the technical requirements used to implement the Password Policy.

## 12.1 Password Length Standards

| Account / System Type | Minimum Requirement |
|---|---|
| Password used as the only authentication factor | 15 characters |
| Standard employee account protected by MFA | 15 characters |
| Customer portal | 15 characters where technically supported |
| PCI-scoped system | At least 12 characters; SecureBank standard is 15 characters |
| Privileged / administrative account | 15 characters minimum plus MFA |
| Machine-generated or vault-managed password | At least 20 characters where supported |
| Maximum supported length | At least 64 characters |

## 12.2 Password Composition and Blocklists

- Password systems must permit spaces and commonly used printable characters.
- Passwords must not be silently truncated.
- Common, predictable, context-specific, and known compromised passwords must be blocked.
- Passwords must be compared against an approved compromised-password blocklist during creation and reset.
- Mandatory uppercase/lowercase/symbol rules are not required unless necessary for a legacy or regulated system.
- PCI-scoped password authentication must meet applicable PCI DSS composition requirements.
- Default and vendor-supplied passwords must be changed before production use.

## 12.3 Password Reset Standards

Password reset mechanisms must:

- Verify the user's identity before reset
- Use single-use reset tokens
- Expire reset tokens within **15 minutes** unless a documented system requirement justifies another value
- Prevent user enumeration through reset messages
- Notify the user after a successful password reset
- Invalidate or review active sessions after a high-risk reset
- Require a new password after use of a temporary credential
- Avoid sending plaintext passwords by email, SMS, chat, or support ticket

Help-desk resets for privileged accounts require enhanced identity verification.

## 12.4 Account Lockout Standards

### PCI-Scoped Systems

PCI-scoped systems must:

- Limit invalid authentication attempts
- Lock or restrict the user ID after no more than **10 failed attempts**
- Maintain the lockout for at least **30 minutes**, or until the user's identity is verified and access is restored through an approved process

### Other Systems

Other internet-facing and high-risk systems must implement:

- Rate limiting
- Progressive delays or risk-based challenges
- Detection of password spraying and credential stuffing
- Alerting for repeated or suspicious authentication failures

## 12.5 Session Timeout Standards

| System Type | Maximum Inactivity Before Lock / Re-authentication |
|---|---|
| Privileged administration / PAM session | 15 minutes |
| Core banking administrative access | 15 minutes |
| Employee workstation | 15 minutes |
| General internal application | 30 minutes unless risk assessment requires less |
| Customer portal | Risk-based; sensitive actions require re-authentication |

Sensitive actions requiring re-authentication include:

- Password or MFA changes
- Privilege changes
- Payment or transfer configuration changes
- Changes to trusted devices
- High-risk administrative operations

## 12.6 MFA Technical Standards

### Approved Methods

Preferred order:

1. **FIDO2/WebAuthn security keys or passkeys**
2. **Approved PKI / certificate-based authentication**
3. **Approved hardware cryptographic token**
4. **Authenticator application using TOTP**
5. **SMS or voice OTP only as an approved exception or fallback**

Biometrics may be used when implemented within an approved MFA solution.

Push-based MFA must include protections against MFA fatigue, such as number matching, additional context, or equivalent controls.

## 12.7 Password Storage Standards

### Approved Hashing

Preferred algorithm:

**Argon2id**

Minimum baseline configuration:

- Memory: **19 MiB**
- Iterations: **2**
- Parallelism: **1**
- Unique salt for every password

Approved alternatives:

| Algorithm | Minimum Standard / Use |
|---|---|
| **Argon2id** | Preferred; minimum 19 MiB memory, 2 iterations, parallelism 1 |
| **scrypt** | Approved when Argon2id is unavailable; use a current approved configuration |
| **bcrypt** | Legacy systems only; work factor 10 or greater |
| **PBKDF2-HMAC-SHA-256** | Approved where FIPS-validated implementations are required; 600,000 or more iterations |

### Prohibited Storage

The following are prohibited:

- Plaintext passwords
- Reversible encryption as a normal password-storage method
- Unsalted hashes
- MD5
- SHA-1
- Fast unsalted SHA-256/SHA-512 password hashes
- Unapproved proprietary password hashing schemes

### Additional Protection

- Each password must use a unique cryptographic salt.
- A pepper may be used as an additional defence-in-depth control.
- If used, a pepper must be stored separately from the password database in an approved secrets vault or hardware security module (HSM).
- Password hashes must be protected using least-privilege access controls.
- Hashing work factors must be reviewed periodically and increased as hardware capability changes.

## 12.8 Password Manager and Secrets Standards

### Employee Password Managers

Approved enterprise password managers must:

- Require MFA
- Encrypt vault contents
- Support unique password generation
- Enforce enterprise access controls
- Provide administrative logging
- Support secure account recovery
- Be centrally managed where possible

Users must not store SecureBank credentials in unapproved consumer password managers.

### Application and System Secrets

- Application credentials must not be hard-coded into source code or scripts.
- Secrets must not be committed to source-code repositories.
- Application and service credentials must be stored in an approved secrets-management platform.
- Access to secrets must be logged and restricted according to least privilege.
- Secrets must be rotated when exposure is suspected.

## 12.9 Privileged Access Management Standards

Privileged credentials must be managed using the approved PAM platform where technically possible.

PAM should support:

- Credential vaulting
- Automatic credential rotation
- MFA
- Role-based access
- Time-limited or just-in-time access where supported
- Audit logging
- Session recording or monitoring for high-risk administration
- Approval workflows for sensitive access
- Emergency access procedures

Privileged users must maintain separate standard and administrative accounts.

Default, shared, and generic privileged accounts must be disabled or strictly controlled.

## 12.10 System-Specific Baseline

| System | Password / Authentication Baseline |
|---|---|
| **Core Banking System** | 15+ character password, MFA, 15-minute inactivity timeout, enhanced logging, privileged access through PAM |
| **Customer Portal** | 15+ character password where supported, compromised-password screening, rate limiting, secure reset process, MFA available and risk-based enforcement |
| **Employee Workstations** | 15+ character password, MFA where supported, 15-minute automatic lock |
| **Administrative Systems** | 15+ character password, phishing-resistant MFA preferred, PAM, 15-minute timeout, enhanced logging |
| **Development Environment** | 15+ character password, MFA, no hard-coded credentials, approved secrets management |
| **PCI / CDE Systems** | Meet all applicable PCI DSS Requirement 8 controls |

## 12.11 Logging and Monitoring

Authentication systems must log, where applicable:

- Successful and failed logins
- Account lockouts
- Password resets and changes
- MFA enrolment and changes
- MFA failures
- Privileged-access events
- PAM credential checkout
- Suspicious authentication patterns

Security monitoring should alert on:

- Password spraying
- Credential stuffing
- Repeated lockouts
- Unusual login patterns
- Suspicious privileged-access attempts
- Unexpected MFA changes

Passwords, reset tokens, OTP values, and other authentication secrets must not be written to logs.

## 12.12 Review and Testing

Technical password and authentication controls must be reviewed:

- At least annually
- After significant changes to authentication infrastructure
- After major security incidents
- When regulatory requirements change
- When updated security guidance materially changes recommended controls

Password hashing parameters must be periodically benchmarked and adjusted to maintain an appropriate balance between security and system performance.
